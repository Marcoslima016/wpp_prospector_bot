# conversation-reasoning Specification

## Purpose

Define how the platform understands inbound WhatsApp messages from leads using an LLM and produces contextual replies, classifying the lead's intent along the way, so conversations can be conducted automatically instead of manually.

## Requirements

### Requirement: Automated reply to inbound one-to-one messages
The system SHALL generate and send a contextual reply, based on LLM reasoning, in response to an inbound one-to-one message received on a paired WhatsApp session.

#### Scenario: Lead sends a direct message
- **WHEN** a lead sends a one-to-one WhatsApp message to a paired session
- **THEN** the system generates a reply via LLM reasoning and sends it back to that lead

### Requirement: Group and self-originated messages excluded
The system SHALL NOT trigger automated reasoning or reply generation for messages originating from a group chat or from the paired session's own account.

#### Scenario: Message arrives in a group chat
- **WHEN** a message is received in a group chat that a paired session belongs to
- **THEN** the system does not generate or send an automated reply for that message

#### Scenario: Message is sent by the paired account itself
- **WHEN** a message event originates from the paired session's own account (e.g., sent from another linked device)
- **THEN** the system does not generate or send an automated reply for that message

### Requirement: Conversation history informs each reply
The system SHALL account for the prior messages exchanged with a lead when generating a reply, not only the most recently received message in isolation.

#### Scenario: Lead sends a follow-up message
- **WHEN** a lead sends a new message in a conversation that already has prior exchanged messages
- **THEN** the reply generated by the system reflects the context of those prior messages, not just the latest one in isolation

### Requirement: Conversation history persists across restarts
The system SHALL retain a lead's conversation history across a platform restart, so that reasoning after a restart still has access to messages exchanged before the restart.

#### Scenario: Platform restarts mid-conversation
- **WHEN** the platform restarts after having exchanged one or more messages with a lead
- **THEN** subsequent replies to that lead still account for the messages exchanged before the restart

### Requirement: Lead intent classification
The system SHALL classify the lead's intent, for each inbound message processed, into one of: Interessado, Sem Interesse, Dúvida, or Opt-out.

#### Scenario: Lead expresses interest
- **WHEN** a lead's message expresses interest in the offering
- **THEN** the system classifies that message's intent as Interessado and records it as part of the conversation's history

#### Scenario: Lead asks to stop being contacted
- **WHEN** a lead's message asks to stop being contacted (e.g., "sair", "parar", "não tenho interesse")
- **THEN** the system classifies that message's intent as Opt-out and records it as part of the conversation's history

### Requirement: Intent classification does not alter automated behavior yet
The system SHALL persist the classified intent as part of the conversation's history without changing the automated reply behavior based on that classification.

#### Scenario: A lead's message is classified as Opt-out
- **WHEN** a lead's message is classified as Opt-out
- **THEN** the system still records the classification, and continues generating automated replies to that lead's subsequent messages in the same way as for any other classification

### Requirement: Replies respect existing outbound throttling
The system SHALL deliver an automatically generated reply through the platform's existing outbound throttling and volume controls, rather than sending it immediately and unconditionally.

#### Scenario: An automated reply is generated while a session is still within its warmup ramp
- **WHEN** the system generates an automated reply for a session that has not yet completed its warmup ramp
- **THEN** the reply is subject to the same per-session and daily volume limits already enforced for other outbound messages

### Requirement: Externally configurable reasoning behavior
The system SHALL derive the instructions guiding the LLM's behavior (system prompt) and the specific LLM model used from external configuration, allowing that configuration to be updated without a code change.

#### Scenario: Administrator updates the reasoning configuration
- **WHEN** an administrator updates the external configuration defining the system prompt or the model used for reasoning
- **THEN** subsequent automated replies use the updated configuration
